# impact-report — 변경/장애 영향 보고 정리

## Overview

크로스 서비스 PR·이슈·장애 분석을 **읽는 사람이 결론부터 영향까지 한 번에 파악**하도록 고정된 5단 구조로 정리한다. 핵심 원칙: **결론 먼저, 비즈니스·임팩트 관점 우선, 사실은 검증 후 기재, 영향은 서비스별로 명시.**

> **독자 가정**: 보고서의 1차 독자는 코드를 안 보는 사람(PM·운영·타팀)이다. "무엇이/누구에게 영향이었나, 어떻게 처리됐나"가 먼저고, 파일·메서드·코드 심볼은 **꼭 필요한 핵심 1~2개로 최소화**한다. 코드 디테일이 필요하면 PR 링크로 위임.

## When to Use

- PR/Sentry/장애 분석을 끝낸 뒤 팀에 보고·공유할 때
- "이 PR 정리해줘", "영향도 정리", "슬랙에 올려줘" 등 요청
- 여러 서비스(InAPI ↔ banking-loan ↔ banking-report 등)가 얽힌 변경의 파급을 전달할 때

**Skip**: 단일 파일 사소한 수정, 커밋 메시지로 충분한 경우.

## 5단 구조 (고정 — 순서·제목 유지)

```
🔧 **[<서비스>] <비즈니스 관점 한 줄 제목>** <PR/이슈 링크>

**결론**
<무슨 문제였고(업무·운영 언어로), 무엇을 어느 방향으로 처리했는지 1~3문장. 기능 장애인지 노이즈인지 성격도 한 마디로. 읽는 사람이 여기서 멈춰도 핵심을 안다.>

**영향 범위 (누가/무엇이)**
<운영/사용자/데이터 관점 영향. 기능은 정상이었는지, 누구에게 어떤 불편/리스크였는지, 재현 여부, 누적·확산성. 코드 아닌 "결과" 언어로.>

**호출 경로**
<요청 주체 → 서비스 A → 서비스 B …. 흐름 이해에 필요한 수준만. 엔드포인트/토픽은 1개 레벨로 간단히, 백틱.>

**원인 (비즈니스 관점)**
<왜 그 상태가 됐는지를 업무 흐름으로 설명. "어떤 상황의 데이터가 / 어떤 조건에서 / 무슨 결과". 파일·메서드명은 꼭 필요하면 1개만, 나머지는 동작·의미로 서술.>

**조치 및 근거**
<바꾼 내용을 효과 중심으로 + 그렇게 한 이유. 운영자 오해 방지·안전성 보존 등 의사결정 근거. 검증 결과(리뷰/테스트 통과)도 한 줄.>

**다른 서비스 영향**
<서비스별로. 영향 있으면 정도까지. 영향 없으면 "코드 변경 없음 / 동작 차이 없음"이라고 반드시 명시.>
```

## 작성 절차

1. **컨텍스트 수집**
   - PR: `gh pr view <num> --json title,body,url` + `git show`/diff로 실제 변경 확인
   - Sentry: `sentry-debug` 산출물 또는 이슈 데이터(발생 수/기간/환경)
2. **사실 검증 (필수)** — "다른 서비스 영향"과 "조치 근거"에 들어가는 **타 레포 코드 주장은 추측 금지.** 해당 레포에서 `grep`/`Read`로 직접 확인한 사실만 기재 (예: "consumer가 409를 retry한다"면 그 consumer의 `@RetryableTopic`·에러 매핑을 열어 확인). 확인 못 한 항목은 "확인 필요"로 표기.
3. **5단 작성** — 위 구조 그대로. 결론을 가장 먼저, 가장 짧게.
4. **(선택) Slack 게시** — 아래 규칙.

## 품질 규칙

- **결론 우선**: 결론 섹션만 읽어도 의사결정이 되도록. 경위·시도과정은 넣지 않는다.
- **비즈니스 언어 우선, 코드 최소화**: 영향·원인·조치는 "결과/업무" 언어로 먼저 쓴다. 파일·메서드·클래스명은 **핵심 1~2개만** 남기고, 그 외는 동작·의미로 서술한다. 코드 디테일은 PR 링크로 위임. (쓸 때는 백틱: 엔드포인트·토픽·에러코드 등)
- **검증 안 된 수치/기간은 '추정' 명시**: 보관기간·빈도·비율 등 외부 스펙 수치는 **확인 못 했으면 단정 금지.** "관측상 약 1년 전후(추정)"처럼 근거(데이터/문서)와 함께 표기. 데이터에서 역산한 값과 공식 문서 값을 구분한다.
- **영향은 빠짐없이**: 호출 경로에 등장한 각 서비스에 대해 영향을 적는다. **"영향 없음"도 생략 금지** — 안 적으면 "안 봤다"로 읽힌다.
- **사실 vs 결정 분리**: "X는 409를 retry한다"(사실, 검증)와 "그래서 숨기지 않고 409로 명시했다"(결정, 근거)를 섞지 않는다.

## Slack 게시 규칙

Slack MCP 도구 사용 (별도 스킬 없음): `mcp__claude_ai_Slack__slack_send_message_draft`(초안) / `slack_send_message`(전송).

- **채널 미지정이면 묻는다** — 채널명/스레드 URL 없이 전송 금지. `slack_search_channels`로 ID 확인.
- **검토 전이면 draft** — 사용자가 메시지를 아직 검토하지 않았으면 `slack_send_message_draft` 우선. "바로 전송" 명시 시에만 `slack_send_message`.
- **스레드 답글**: 스레드 URL을 받으면 `thread_ts`로 답글.
- Slack 마크다운: `**bold**`, 백틱 코드, `<url|텍스트>` 링크.

## Common Mistakes

| 실수 | 교정 |
|---|---|
| 경위·디버깅 과정을 결론에 나열 | 결론은 "문제 + 처리 방향" 1~3문장만 |
| 파일·메서드·코드 흐름을 그대로 나열 | 비즈니스/결과 언어로 환원, 코드 심볼은 핵심 1~2개만 (나머지 PR 링크 위임) |
| 검증 안 된 수치를 사실처럼 단정 (예: "보관기간 1년") | "추정" 명시 + 근거(데이터 역산/문서) 병기, 또는 확인 후 기재 |
| 타 서비스 영향을 추측으로 작성 | 그 레포 코드를 열어 확인 후 기재, 못 하면 "확인 필요" |
| 영향 없는 서비스 누락 | "코드 변경 없음" 명시 |
| 채널 안 물어보고 전송 | 채널 확인 + 미검토 시 draft |

## 예시 (실제 #17315 — 비즈니스·임팩트 톤)

```
🔧 **[inapi] 통지장 팩스 상태 'Sentry 에러 폭증' 원인 차단 (Sentry #19386)** <github.com/.../pull/17315|PR #17315>

**결론**
관리자가 차주의 통지장(팩스) 발송내역 화면을 열 때마다, 외부 팩스 서비스(popbill)에 "존재하지 않는 요청번호"를 조회해 에러가 반복 발생하던 건. 한 번 어긋난 건은 화면을 열 때마다 계속 재발해 Sentry 에러가 누적됐다(4일간 62건). 해당 건을 '조회불가'로 확정 처리해 반복 조회·에러를 차단. 기능 장애는 아니고 로그/알람 노이즈 문제.

**영향 범위 (누가/무엇이)**
- 운영: 화면 표시는 정상 동작(기능 무해). 다만 의미 없는 에러 알람이 쌓여 실제 장애 알람을 가리는 노이즈가 됨.
- 재현: dev에서도 재현 확인.
- 누적성: 최종 상태로 안 굳은 건이 계속 쌓여, 방치 시 에러가 누적·반복되는 구조.

**호출 경로**
관리자 → admin → inapi GraphQL `/graphql/` → 외부 팩스 서비스(popbill) 상태조회

**원인 (비즈니스 관점)**
팩스 전송 후 최종 결과(완료/실패)가 확정되지 못한 채 "진행 중"으로 남은 건은 화면을 열 때마다 popbill에 상태를 다시 묻는다. 오래된 건(관측상 약 1년 전후, 추정)은 popbill에서 요청번호가 만료돼 조회 자체가 불가 → "조회 실패 → 상태 미확정 → 다음에 또 실패"가 무한 반복.

**조치 및 근거**
조회 불가가 확인된 건은 '조회불가'로 최종 확정 → 같은 건 재조회 안 함(반복 차단). 화면엔 '조회불가 (보관기간 경과)'로 표기해 운영자가 전송 실패로 오해하지 않게 함(실제론 전송됐을 가능성 높음). 조회 불가는 시스템 장애가 아닌 예상 가능 상황이라 알람 레벨 낮춤. 다관점 코드리뷰+독립검증 통과, 머지 블로커 없음.

**다른 서비스 영향**
- admin 프론트엔드: 변경 없음. 상태 문자열을 그대로 표시하는 구조라 신규 표기 정상 노출.
- investment / banking-report / jb-fep: 영향 없음(팩스 미사용).
- popbill(외부): 불필요한 반복 조회 감소. 팩스 전송 동작 변화 없음.
```

> 위 예시는 파일·메서드명을 본문에서 뺐다. 코드 심볼이 꼭 필요하면 1~2개만, 상세는 PR 링크로.
