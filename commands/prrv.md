# 대형 PR 회차 리뷰

대형 PR을 계층 단위 회차로 쪼개 병렬 리뷰하고, 결론을 좌우하는 라인은 메인 세션이 직접 재확인한 뒤 PR 코멘트 초안까지 만든다.

`/ecr` 과는 별개 경로다. `/ecr` 은 한 번에 훑는 종합 리뷰, 이 커맨드는 한 번에 다 볼 수 없는 규모를 회차로 나눠 본다. 20파일 미만이면 `/ecr` 을 쓴다.

## 입력 해석

`$ARGUMENTS` 에서 아래를 뽑는다:

- **PR 번호 또는 URL** — 없으면 현재 브랜치의 PR을 `gh pr view --json number` 로 찾는다. 그래도 없으면 사용자에게 묻는다.
- **회차 지정** (`2회차`, `round 2`, 스코프 설명) — 있으면 Phase 0·1을 건너뛰고 해당 회차만 실행한다. 이전 회차에서 확인된 사실을 전제로 전달해야 하므로, 같은 세션이 아니면 사용자에게 이전 회차 결론을 요청한다.
- 스코프를 직접 지정한 경우(파일 목록) 그대로 존중한다.

한 번에 다 보면 발견율이 떨어진다. **지형 파악 → 회차 분할 → 회차별 병렬 리뷰 → 메인 직접 검증 → 코멘트화** 순으로 진행한다.

## Phase 0 — 지형 파악 (코드 읽기 전)

```bash
gh pr view <N> --json title,author,additions,deletions,changedFiles,commits,baseRefName,headRefName \
  --jq '{title,author:.author.login,additions,deletions,changedFiles,base:.baseRefName,commitCount:(.commits|length)}'
gh pr view <N> --json body --jq .body          # 설계 의도 — 반드시 먼저 읽는다
gh pr diff <N> | git apply --numstat - | sort -k1 -rn   # 파일별 규모 (최종 diff)
gh pr view <N> --json commits --jq '.commits[] | "\(.oid[0:8]) \(.messageHeadline)"'
git fetch origin <head> <base> -q && git rev-parse origin/<head>
```

판단할 것:

- **테스트/프로덕션 비율** — 테스트가 절반이면 실질 리뷰량은 절반이다. 테스트는 케이스 목록만 훑는다.
- **커밋별로 읽을지** — 커밋 메시지에 rename·설계 교체가 보이면 **커밋별 리뷰 금지**. 폐기된 설계를 읽는 시간이 된다. 최종 diff만 본다.
- **stacked PR 여부** — `baseRefName` 이 기본 브랜치가 아니면 base PR을 먼저 확인한다. base가 먼저 배포될 수 있는지가 마이그레이션 위험도를 좌우한다.
- **head SHA를 기록해둔다** — 아래 "운영 함정" 참조.

사용자에게 먼저 지형과 회차 계획을 보고하고, 규모가 `/ecr` 로 충분하면 그렇게 말한다.

## Phase 1 — 회차 분할

회차는 **계층**으로 자른다(파일 수로 자르지 않는다). 계층이 섞이면 리뷰어가 같은 코드를 두 번 읽는다.

전형적인 분할:

| 회차 | 스코프 | 리뷰 관점 |
|---|---|---|
| 1 | 도메인 엔티티 + 영속 어댑터 + 마이그레이션 | 불변식, 상태 전이, 영속 왕복, 스키마 호환 |
| 2 | UseCase + 컨슈머/프로듀서 + 배선 | 정확성, 멱등, 실패 수렴, 트랜잭션·발행 경계 |
| 3 (선택) | 테스트 | 커버리지 공백, 삭제된 테스트 대조, assertion 약화 |

각 회차 3개 리뷰어 병렬. 회차마다 스코프 밖 파일은 "호출 흐름 확인 목적으로만 읽고 finding 대상 아님"을 명시한다.

## Phase 2 — 회차별 병렬 리뷰어

리뷰어 프롬프트에 반드시 포함:

1. **스코프 고정** — 파일 목록 + 라인 규모. 스코프 밖은 finding 금지.
2. **코드 확보 방법** — `git show <ref>:<경로>`. 워킹트리는 PR 이전 상태일 수 있다.
3. **PR 본문을 먼저 읽으라는 지시** — 설계 의도를 모르면 의도된 트레이드오프를 버그로 보고한다.
4. **스킬 직접 로드 지시** — 백엔드면 `backend-code-quality-review`, 도메인 쟁점이면 `domain-modeling-gate`, Kotlin이면 `kotlin-patterns`. 메인이 읽어서 프롬프트에 옮기지 않는다.
5. **이전 회차에서 확인된 사실을 전제로 전달** — "이미 CRITICAL로 보고됐으니 재보고 말고, 이 사실이 이번 스코프 판단에 미치는 영향만 따져라". 중복 발견을 막는다.
6. **메인 세션의 자체 후보는 전달하지 않는다** — 독립 발견 여부가 그 후보의 신뢰도다. 나중에 대조한다.
7. **응답 형식 + "작업이 끝나면 반드시 회신하라"** — 이 문장이 없으면 리포트 없이 idle로 끝나는 경우가 있다.

리뷰어 조합은 규모·민감도로 정한다. 도메인 모델 회차에 security-reviewer는 값이 없고, 마이그레이션이 있으면 api-reviewer가 스키마 호환을 본다. 리뷰 필수 관점은 `rules/common/verification.md` 4항목을 프롬프트에 명시한다.

## Phase 3 — 메인 세션 직접 검증 (건너뛰지 않는다)

**리뷰어 리포트를 그대로 사용자에게 옮기지 않는다.** CRITICAL/HIGH는 결론을 좌우하는 라인을 메인이 직접 읽어 확인한다.

- 인용된 file:line이 실제 그 내용인지
- 주장한 호출 흐름이 실제로 이어지는지 (특히 "이 값이 외부로 나간다" 류)
- 다른 저장소를 거는 주장(예: 상대 서비스가 이 필드를 싣는다)은 그 저장소에서 직접 grep

교차 검증에서 자주 나오는 두 패턴:

- **의도된 트레이드오프를 버그로 보고** — 테스트 주석·PR 본문에 방어 근거가 있는지 확인한다. 있으면 수정 방향이 달라진다(원천을 바꾸지 말고 그 값이 새는 지점을 막는다).
- **리뷰어 주장의 전제가 틀림** — "불변식이 코드에 없다"는 주장은 검사 위치가 다른 함수인 경우가 많다.

critic 계열 에이전트가 리포트를 반환하지 않으면 `SendMessage` 로 형식을 지정해 재요청하고, 두 번 실패하면 메인이 직접 검증하고 **"교차 검증은 직접 확인으로 대체했다"고 사용자에게 밝힌다.**

## Phase 4 — 코멘트화

### 앵커

GitHub 인라인 코멘트는 **diff에 포함된 라인**에만 붙는다.

- 신규 파일(`git diff --name-status` 가 `A`)은 `position == line`
- 수정 파일은 `gh api .../pulls/<N>/comments` 로 기존 코멘트의 `position` 을 보고 형식을 맞춘다
- 같은 이야기가 여러 파일에 걸치면 **수정이 들어갈 파일에 상세 코멘트 1개 + 나머지에 1줄 포인터**

### 톤

| Severity | 접두 | 톤 |
|---|---|---|
| CRITICAL | 🔴 | 단호 + 머지 차단 사유 명시 |
| HIGH | 🟠 | 문제 지적 + 대안 |
| MEDIUM | 💡 | 제안, 선택권 |
| nit | 💭 | 무시 가능 표시 |

**심각도가 데이터 상태에 달렸으면 블로커로 단정하지 않는다.** 확인 SQL과 함께 조건부로 쓴다 — "0행이면 형식적 조치로 충분, 행이 있으면 머지 전 필수". 단정하면 작성자가 방어에 에너지를 쓴다.

질문이 아니라 관찰 + 제안으로 쓴다. 작성자 의도를 존중해 "이 부분의 의도가 ~라면" 형태로 가정을 명시한다.

### 사용자 말투 미러링

사용자가 직접 남긴 코멘트가 이미 있으면 **그 말투를 추출해 맞춘다.** `gh api .../reviews/<id>/comments` 로 기존 코멘트를 읽고 어미·문장 구조·기호 습관(`?` 앞 공백, `!` 종결, `??`)을 그대로 따른다. 톤이 섞이면 작성자가 다른 사람이 쓴 걸 알아챈다.

### 남기는 규칙

- **기본은 초안만 채팅으로 제공한다.** PR에 직접 쓰지 않는다 (`CLAUDE.md` §6).
- 사용자가 명시적으로 지시하면 **PENDING 리뷰까지만** 만든다. `submit` 은 하지 않는다.
- 기존 코멘트 본문을 API로 덮어쓰지 않는다 — 되돌리기 어렵다. 수정은 초안만 주고 사용자가 편집한다.
- PENDING 리뷰는 사용자당 PR당 1개다. 이미 있으면 새로 만들지 말고 그 리뷰에 추가한다.

### 코멘트 개수 다이어트

발견을 다 남기면 핵심이 묻힌다. 남기기 전에 분류한다:

- **필수** — 리뷰에서만 잡히는 결함(예외·알람·테스트 어디에도 안 걸리는 것)
- **기존 코멘트에 이어붙임** — 같은 버그의 다른 입구, 작성자 반박을 미리 막는 사실
- **생략** — 런타임 버그가 아닌 모델·주석 불일치. 나중에 리팩토링 코멘트로 묶는다

"보강하면 더 좋다"와 "보강해야 살아남는다"를 구분해서 사용자에게 알린다. 후자는 안 하면 finding이 죽거나 잘못된 수정을 부른다.

## 운영 함정

- **브랜치 이동** — 서브에이전트의 `git fetch` 가 remote ref를 갱신한다. 리뷰 중 head SHA가 바뀔 수 있다. 보고 전 `git rev-parse origin/<head>` 로 Phase 0에서 기록한 SHA와 비교하고, 다르면 `git log --oneline <old>..<new>` 로 무엇이 바뀌었는지·이전 회차 결론이 여전히 유효한지 확인한다.
- **`gh pr diff <N> -- <path>` 는 지원되지 않는다** (`accepts at most 1 arg`). 파일별 diff는 `git diff <base-ref> <head-ref> -- <path>`.
- **`gh pr diff --patch` 는 커밋별 patch를 이어붙여 출력한다** — numstat을 돌리면 같은 파일이 여러 번 집계된다. 최종 규모는 `--patch` 없이.
- **zsh에서 `$VAR:path` 는 `:r` 히스토리 수정자와 충돌한다.** `git show "${R}:${P}"` 처럼 중괄호를 쓴다.
- **워킹트리는 PR 브랜치가 아니다.** 리뷰어가 디스크를 읽으면 base 코드를 본다. 프롬프트에 `git show <ref>:<경로>` 를 명시한다.

## 산출물

사용자에게 줄 것:

1. **통합 결과** — 머지 전 / 후속 / 작성자 질문 / 확인 필요(SQL) / 잘 된 부분
2. **코멘트 초안** — 앵커(file:line) + 본문. 복사해서 바로 쓸 수 있게
3. **리뷰 신뢰도 메모** — 무엇을 직접 확인했고, 무엇이 리뷰어 근거이며, 어떤 주장을 정정했는지. 삼중 독립 발견은 명시(신뢰도 신호)

`/impact-report` 로 팀 공유용 요약이 필요하면 이어서 호출한다. 리뷰 문서 보관은 `/docs-save`.
