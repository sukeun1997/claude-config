현재 브랜치의 PR을 아래 템플릿 형식으로 작성하거나 업데이트해줘.
PR 번호가 주어지면 해당 PR을, 아니면 현재 브랜치의 PR을 찾아서 업데이트해.

## 작업 순서

1. 베이스 브랜치 판별: `develop` 브랜치가 있으면 develop, 없으면 `main` 사용
2. `gh pr view`로 현재 PR 정보 확인
3. `gh pr diff --name-only`로 변경 파일 목록 확인
4. `git log {base}..HEAD --oneline`으로 커밋 히스토리 확인
5. 변경 내용을 분석하여 아래 템플릿에 맞게 PR 제목과 본문 작성
6. **본문 파일 작성 후 `gh pr edit --body-file`로 PR 업데이트** — Write 도구로 `/tmp/pr_body_<num>.md`에 본문 작성 → `gh pr edit <num> --body-file /tmp/pr_body_<num>.md`. `--body "$(cat <<EOF ... EOF)"` 형태는 금지 (백틱 escape 문제로 코드블록/인라인 코드 깨짐). 신규 PR 생성 시 `gh pr create --body-file` 동일 적용.
7. 업데이트 직후 `gh pr view <num> --json body --jq .body | head`로 백틱/코드블록 정상 렌더 검증

## 작성 원칙 (핵심 위주, 간결)

- 요약은 **3-bullet 이내**. 무엇을, 누구와의 짝 PR인지, 격리/안전 정책 한 줄.
- 주요 변경사항은 **모듈/디렉터리별 그룹핑** + 줄당 한 줄 bullet. 의도와 결정 근거를 짧게.
- 호환성·연동 검증, 정책 차이, 종료 경로 등 **검증 결과는 표**로 정리.
- 스프린트 명칭(STEP, Phase, 스펙 §, Q1·Q2 등 내부 결정 ID), plan 문서 링크는 **본문에 노출하지 않는다** — 코드와 PR이 정답이고 plan 은 잠재 정보.
- 테스트 테이블은 **테스트 클래스 단위**로, 검증 항목을 한 줄로.
- 필요 작업은 완료(`[x]`)·미완료(`[ ]`) 모두 포함하되, 한 줄짜리 행동 단위.
- 1-3 sentence 의 "왜 이 PR 인가" 가 보이면 충분. 배경 장문 금지.

## PR 템플릿

```
## 요약

- [무엇을 — 1줄 동사 중심]
- 짝 PR: [repo#NUM](URL) (있는 경우)
- [격리/안전/롤백 정책 한 줄] (있는 경우)

### 주요 변경사항

**`경로/디렉터리`** — 한 줄 요약:
- 구체 변경 1
- 구체 변경 2

**`다른/경로`** — 한 줄 요약:
- ...

### [짝 PR 호환성 / 연동 검증]  (있는 경우)

| 경계면 | 결과 |
|---|---|
| Endpoint | ✅ ... |
| Payload | ✅ ... |
| Enum/계약 | ✅ ... |

### 테스트

| 모듈 | 테스트 클래스 | 검증 항목 |
|------|-------------|----------|
| `모듈명` | `테스트클래스명` | 핵심 항목들 콤마로 |

## 본 스프린트 제외 (있는 경우)

- 후속 작업 / 다음 단계 항목

## 필요 작업

- [x] 완료
- [ ] 수동 검증 / 후속

## 참고

- JIRA [TICKET-ID](URL) (있는 경우)
- 짝 PR (요약에 이미 있으면 생략)
```

## 규칙

- PR 제목은 conventional commit 형식: `feat:`, `fix:`, `refactor:`, `test:`, `chore:` 등
- PR 제목은 70자 이내로 간결하게
- 주요 변경사항은 모듈별로 그룹핑, **각 그룹 5줄 이내**
- 호환성/테스트 테이블은 해당 정보가 있는 경우만 포함
- 참고 링크는 JIRA 티켓 또는 짝 PR 이 있는 경우만 포함
- 본문에 plan/spec 문서 경로, "본 스프린트", "STEP N", §-번호 표기 등 내부 작업 메타 노출 금지
